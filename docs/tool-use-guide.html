Tool-Use in Claude API

Concrete Examples to Master Schema Design and Tool Selection

1. How the Tool-Use Loop Actually Works

The most important thing to understand: Claude does not run the tools. Claude reads your tool definitions, decides which tool fits the situation, and tells your application what to call.

The Loop Sequence

Your app: Define tool schemas and send them to Claude
Claude: Reads schemas, analyzes the request, returns a tool_use block
Your app: Execute the tool with the arguments Claude specified
Your app: Send tool_result back to Claude with the execution result
Claude: Continues with the result as context for next response
⚠️ Critical Point

If your application doesn't return the result correctly (or at all), Claude never gets the data it asked for, and the loop breaks. The boundary between what Claude owns and what your code owns is where most bugs live.

Real Code Example: Building a Tool-Use Loop

Python with Anthropic SDK
from anthropic import Anthropic

client = Anthropic()

# Step 1: Define your tools
tools = [
    {
        "name": "get_weather",
        "description": "Get current weather for a location",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {"type": "string"}
            },
            "required": ["location"]
        }
    }
]

# Step 2: Send initial message
messages = [
    {"role": "user", "content": "What's the weather in Paris?"}
]

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    tools=tools,
    messages=messages
)

# Step 3: Handle tool calls in a loop
while response.stop_reason == "tool_use":
    # Find the tool_use block
    tool_use = next(
        block for block in response.content
        if block.type == "tool_use"
    )

    # Step 4: Execute the tool
    if tool_use.name == "get_weather":
        result = get_weather_function(
            location=tool_use.input["location"]
        )

    # Step 5: Send result back to Claude
    messages.append({"role": "assistant", "content": response.content})
    messages.append({
        "role": "user",
        "content": [
            {
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": str(result)
            }
        ]
    })

    # Continue the conversation
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=1024,
        tools=tools,
        messages=messages
    )

# Final response
print(response.content[0].text)
The Critical Pairing Rule Every tool_use block from Claude MUST be answered with a tool_result block in the immediately following user turn. The IDs must match exactly. Missing this pairing causes an API validation error.

2. Message Block Structure: What Goes Where

A tool-use conversation is built from structured blocks, not plain text. Understanding the block types and their pairing rules is essential.

The Four Block Types

Block Type Who Creates It Contains Critical Rule
text Claude Claude's prose response May appear alongside tool_use in same turn. You must preserve it when saving conversation history.
tool_use Claude Tool name, unique ID, input arguments MUST be answered by tool_result with matching ID in next user turn
tool_result Your app Matching tool_use_id, result content, optional is_error flag tool_use_id must match exactly. This is how Claude connects results to calls.
thinking Claude (extended thinking) Claude's internal reasoning Pass back unchanged (verified by signature). Any edit breaks it.

Real Message Structure Example

JSON Structure
{
  "messages": [
    {
      "role": "user",
      "content": "Get the weather for London and Paris"
    },
    {
      "role": "assistant",
      "content": [
        {
          "type": "tool_use",
          "id": "call_1",
          "name": "get_weather",
          "input": {"location": "London"}
        },
        {
          "type": "tool_use",
          "id": "call_2",
          "name": "get_weather",
          "input": {"location": "Paris"}
        }
      ]
    },
    {
      "role": "user",
      "content": [
        {
          "type": "tool_result",
          "tool_use_id": "call_1",
          "content": "London: 15°C, cloudy"
        },
        {
          "type": "tool_result",
          "tool_use_id": "call_2",
          "content": "Paris: 18°C, sunny"
        }
      ]
    },
    {
      "role": "assistant",
      "content": [
        {
          "type": "text",
          "text": "London is 15°C and cloudy, while Paris is 18°C and sunny."
        }
      ]
    }
  ]
}
💡 Parallel Tool Calls

Notice that Claude issued two tool_use blocks in a single turn (for London and Paris). Both need tool_result blocks in the next user turn. This is called "parallel tool calling" — your code can execute them concurrently since they're independent, then return both results at once.

3. Schema Anatomy: How Claude Picks the Right Tool

Claude picks tools based on three things in this order: name, description, and input schema. The description is where most selection decisions happen.

The Three Parts of a Schema

✓ Good Schema 
{
  "name": "get_account_balance",
  "description": "Retrieve the current account balance for a specific account ID. Use this when the user asks about their account balance or available funds. Do not use this for transaction history or payments.",
  "input_schema": {
    "type": "object",
    "properties": {
      "account_id": {
        "type": "string",
        "description": "The account ID"
      }
    },
    "required": ["account_id"]
  }
}
✗ Bad Schema 
{
  "name": "get_data",
  "description": "Use this to find information",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {"type": "string"}
    }
  }
}

Why the Difference Matters

Aspect Good Schema Bad Schema
Name Specific: get_account_balance Generic: get_data
Description Includes when to use AND when NOT to use Vague: "find information" could mean anything
Required fields Only account_id is required — the essential input No required array — Claude might guess at inputs
Result Claude picks correctly 95%+ of the time Claude confuses this with other tools that "find information"
The Exclusion Condition Rule A good description tells Claude not just what a tool does, but what it does NOT do. "Use for X, do not use for Y" is more powerful than "use for X" alone.

4. Common Schema Design Mistakes

Mistake #1: Overlapping Tool Descriptions

✗ Both sound the same 
Tool 1: "Use this to find information"

Tool 2: "Use this to search for data"
✓ Clear distinction 
Tool 1: "Search the knowledge base when the user asks a question that requires looking up current information. Do not use this if a prior search in this session already covered the question."

Tool 2: "Retrieve a result that was already fetched during this session. Only use if search_knowledge_base was called earlier for the same query."

Mistake #2: Making Fields Required When They Shouldn't Be

✗ Forces Claude to guess 
{
  "input_schema": {
    "properties": {
      "user_id": {"type": "string"},
      "filter": {"type": "string"},
      "sort_order": {"type": "string"},
      "page_size": {"type": "integer"}
    },
    "required": [
      "user_id",
      "filter",
      "sort_order",
      "page_size"
    ]
  }
}

Problem: Claude has no basis to fill in "filter" or "sort_order", so it invents values that may not make sense.

✓ Only essentials required 
{
  "input_schema": {
    "properties": {
      "user_id": {"type": "string"},
      "filter": {"type": "string"},
      "sort_order": {"type": "string"},
      "page_size": {"type": "integer"}
    },
    "required": ["user_id"]
  }
}

Better: Claude omits optional fields if it doesn't have the information, instead of guessing.

Mistake #3: Description is Too Vague or Too Long

✗ Too vague (1 sentence) 
"Get user information"

Does this mean profile data? Preferences? Contact info? Claude has to guess.

✗ Too long (loses signal) 
"This tool retrieves user information from the database. It was implemented in Q2 2024 and uses the legacy user_info endpoint which was deprecated in favor of the new unified user service. When calling this tool, you may pass user_id or email. Note that the tool was designed for internal use and some fields may be null. The endpoint returns a JSON object with fields like name, email, phone, address, and preferences. You should call this before calling get_user_preferences because of caching behavior."

Too much detail. Claude can't find the decision rule in the noise.

✓ Just right (3-4 sentences) 
"Retrieve a user's profile data including name, email, and account creation date. Use this when the user asks about their profile or personal information. Do not use this for preferences or notification settings — those have separate tools. Example user_id: 'usr_12345'."

Clear, includes a "do not use" clause, and gives an example of valid input format.

5. Real-World Scenario: A Support Ticket Processor

Let's build the system from your project: a tool that helps classify support tickets.

The Tools We Need

{
  "tools": [
    {
      "name": "classify_ticket",
      "description": "Analyze a support ticket and classify it by category (billing, technical, escalation) and urgency (low, medium, high, critical). Use this when a raw support ticket text is provided. Returns a classification with reasoning. Do not use this if the ticket has already been classified.",
      "input_schema": {
        "type": "object",
        "properties": {
          "ticket_text": {
            "type": "string",
            "description": "The full text of the support ticket"
          },
          "ticket_id": {
            "type": "string",
            "description": "Optional ID to track which ticket this is"
          }
        },
        "required": ["ticket_text"]
      }
    },
    {
      "name": "escalate_ticket",
      "description": "Escalate a ticket to the urgent queue when it's classified as 'critical' urgency. Use only after classify_ticket determines the urgency is critical. Do not use for any other urgency levels.",
      "input_schema": {
        "type": "object",
        "properties": {
          "ticket_id": {"type": "string"},
          "reason": {"type": "string"}
        },
        "required": ["ticket_id", "reason"]
      }
    }
  ]
}

How Claude Uses These Tools

User sends: "Our entire team is locked out of the account and we have a client demo in 20 minutes. Please help ASAP!"
Claude reads the tools and decides: "This looks like a classification task → classify_ticket"
Claude outputs: tool_use block with name="classify_ticket" and the ticket text
Your app calls your actual function, gets back: {category: "technical", urgency: "critical"}
Your app sends tool_result back to Claude with the classification
Claude sees urgency="critical" and decides: "Now I should escalate_ticket"
Claude outputs: tool_use block with name="escalate_ticket"
Your app executes escalate_ticket, returns confirmation
Claude writes final response: "This ticket has been classified as critical technical issue and escalated to the urgent queue"
🎯 Why These Tools Work Together

escalate_ticket depends on the output of classify_ticket. The schema descriptions make this dependency clear: "Use only after classify_ticket determines the urgency is critical." Claude sees these exclusion conditions and makes the right sequencing decision automatically.

6. Schema Design Decision Table

Design Decision Right Approach Why It Matters
Subtask Dependency
Does one tool's output feed the next?		 Sequential: Design with separate turns so first result is available before the next call. Claude will naturally make sequential calls when it sees the dependency in your descriptions. If you force parallel when there's a real dependency, the second call will have garbage inputs because the first result isn't available yet. Conversely, don't force sequential when calls are actually independent — let Claude run them in parallel for speed.
Required Fields Mark only fields as required if the tool literally cannot be called without them. Everything else goes in optional. Every required field forces Claude to fabricate a value if it doesn't have one. Over-marking forces bad tool inputs.
Optional Fields Use for parameters with sensible defaults or where absence carries meaning (e.g., "filter" with no value means "all items"). Optional fields let Claude omit information it doesn't have. If a field is useful only sometimes, make it optional.
Description Length 3-4 sentences: what it does, when to use it, when NOT to use it, one example of valid input if format matters. Too short = Claude guesses. Too long = Claude loses the signal in the noise.
Overlapping Parameters If two tools take the same parameter shape, add disambiguating language: name the domain or trigger each tool is for in the description. Claude routes on name + description. When signatures match, description is all Claude has. Similar-sounding descriptions become indistinguishable.

7. MCP: When to Use Existing Tools Instead of Building Your Own

Before you write tool schemas from scratch, ask: does an MCP server already exist for this?

What is MCP?

The Model Context Protocol is a standard way to publish tool definitions. Instead of you writing schemas and execution functions, an MCP server does it. You connect to the server, receive the tool list, and Claude selects among those tools using the same description-based routing.

Example: GitHub Integration

✗ Manual approach 
You write:
- Schema for list_repos
- Schema for create_issue
- Schema for update_pr
- Schema for get_commits
- ... 50 more schemas
- And maintain all of them as GitHub's API changes
✓ MCP approach 
1. Connect to MCP server for GitHub
2. Server sends you all 50+ tool definitions
3. Claude selects among them
4. Server maintainer keeps tools in sync with GitHub API

When to Use MCP

Use MCP when: A well-maintained server exists for the service, covers the operations you need, and is actively maintained. You get breadth without maintenance overhead.

When to Write Schemas Manually

Write schemas manually when: No MCP server exists, or you need precise control over scope and descriptions that a general-purpose server doesn't provide.

When to Use Both

Hybrid approach: Connect to an MCP server for breadth, then manually tune the descriptions of the specific tools you route to. Use MCP's allowlisting feature to hide tools you don't need, narrowing Claude's surface area.

Summary: The Three Rules

Rule 1: The Loop Must Close Claude writes tool_use blocks. Your code must execute them and return tool_result blocks. Every tool_use needs a matching tool_result. If the loop breaks, the conversation stalls.
Rule 2: Descriptions Drive Selection Claude picks tools based on name, description, and schema in that order. The description is where the real decision-making happens. Include "do not use this for X" to disambiguate overlapping tools.
Rule 3: Design for the Real Dependency If one tool depends on another's output, write descriptions that make that dependency clear. Claude will sequence calls correctly. If tools are independent, let Claude run them in parallel.
